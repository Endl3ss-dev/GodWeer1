## 2026-10-25 — Скрипты: кольцо в стеке блоков и OutOfMemoryError в тике

### Находка (из логов, не из предположений)

`run/logs/2026-10-24-6.log` (сервер авторизации, 20:26–20:30) и `debug.log` содержат
падение клиента:

```
[20:29:30] [Render thread/ERROR] (net.minecraft.client.Minecraft) Out of memory
java.lang.OutOfMemoryError: Java heap space
    at java.util.ArrayList.grow(ArrayList.java:240)
    at com.google.gson.JsonArray.add(JsonArray.java:117)
    at swerve.script.ScriptStore.encodeChain(ScriptStore.java:294)
    at swerve.script.ScriptStore.save(ScriptStore.java:256)
    at swerve.script.ScriptStore.tick(ScriptStore.java:152)
```

Корень — `ScriptBlocks.detach`: открепляя блок, метод отдавал родителю
`target.getNext()`, то есть блоки под `target` оставались и в исходном стеке, и в
перетаскиваемой цепочке. Возврат цепочки на место (`insert`) замыкал список в
кольцо: `tail.next` указывал на прежнюю голову. Дальше `encodeChain` шёл по кольцу
и добавлял объекты в `JsonArray`, пока не кончалась память. Воспроизводилось
простым кликом по блоку: `finishDrag` при `!moved` возвращает блок в исходную
позицию, а `beginDrag` уже открепил его.

### Что изменено

| Файл | Причина |
| --- | --- |
| `script/ScriptBlocks.java` | `detach` рвёт связь родителя (`previous.next = null`, `holder.head = null`) — цепочка под блоком уезжает вместе с ним, как в Scratch, но в исходном стеке её больше нет; `insert` возвращает `boolean` и отказывает, если цепочку вкладывают в неё саму (проверка головы контейнера добавлена к прежней проверке C-блока); обходы в `at`/`contains`/`indexOf`/`holderOf`/`detach` ограничены `MAX_CHAIN` |
| `script/ScriptBlock.java` | `MAX_CHAIN = 4000` и пределы в `chainLength`/`tail`/`flatten`: обход испорченной модели не может крутиться вечно |
| `script/ScriptStore.java` | `encodeChain` получил предел длины (`MAX_BLOCKS` на весь файл) и глубины (`MAX_DEPTH`), усечение пишется в лог один раз; `decodeChain` использует ту же константу `MAX_DEPTH` вместо литерала `200` |
| `ui/script/ScriptScreen.java` | новый `attach(holder, index, block)`: при отказе вставки цепочка уходит в конец корневого стека, иначе откреплённый блок молча исчез бы из редактора; все восемь точек вставки переведены на него |
| `docs/Scripts.md` | раздел «Инварианты модели стеков» и разбор этого падения |
| `tests/check_script_blocks.py` | новая проверка (см. ниже) |

### Чем проверено

```
check_script_blocks        найдено: 0   (статика + перебор перетаскиваний + мутация)
check_script_blocks /tmp/mut/... → код 1 на копии со старым detach:
    «в родителя снова подставляется target.getNext()», «голова контейнера не
     обнуляется», «связь родителя не рвётся» — проверка ловит исходный баг
check_syntax               файлов: 235, находок: 0
check_types                файлов: 235, классов: 275, находок: 0
check_scope                найдено: 0
check_mc_api               static references checked: 693, shadow fields verified: 11
check_config / check_killaura / check_pvp_utils / check_speed / check_acd   0
check_hotpath              105 жёстких (105 в исключениях), информационных 116
check_hotpath_mutations    8/8 поймано
check_acd_mutations        35/35
check_speed_mutations      18/18
```

`check_script_blocks.py` состоит из трёх частей: статические требования к исходникам
(в `detach` нет `target.getNext()`, есть `setNext(null)`/`setHead(null)`;
`encodeChain` ограничен бюджетом и глубиной; `ScriptScreen` не вызывает
`ScriptBlocks.insert` вне `attach`); перебор перетаскиваний в модели (стек длины
1–4, все пары «взять i — положить в j», вложенные пасты) с проверкой ацикличности,
сохранности и уникальности блоков; мутация «прежний detach + прежний insert»,
которая обязана воспроизвести кольцо (воспроизводит в 3 из 6 случаев).

### Ограничения

* Это **модельная** проверка алгоритма, а не исполнение Java: JDK в песочнице нет,
  `javac`/`./gradlew build` недоступны (см. журнал ниже: Temurin → `curl 35`).
  Порт написан построчно по `ScriptBlocks`, но расхождение порта и оригинала
  проверка не заметит — статическая часть привязана к конкретным конструкциям.
* Воспроизведение в рантайме не выполнено: подтверждение — стек из лога клиента и
  разбор кода, а не запуск исправленной сборки на машине владельца.
* `run/logs` — единственный источник рантайм-факта; новых прогонов после этой
  правки нет.

### Следующее действие

На машине владельца: `./gradlew build`, затем в редакторе скриптов кликнуть по
первому блоку цепочки (детект регрессии), перетащить блок в собственную «пасть»
(должен уехать в конец стека, не исчезнуть), перезапустить клиент и проверить, что
`config/swerve/scripts.json` сохранился без усечения (в логе не должно быть
`Script stack is longer than`).

## 2026-10-26 — AntiCheatDetector: диагностика событий античита (12 классов, 2 миксина)

### Зачем

Модуль-накопитель того, что сервер уже показал клиенту: системные сообщения, причина
отключения, серверная коррекция позиции, выданная скорость, неизвестные каналы полезной
нагрузки, ошибки обработки пакетов. Задача — наблюдение и выгрузка (`Copy All Logs`,
файл, локальный чат), а не обход: см. `docs/AntiCheatDetector.md` §5.

### Что доказано (байткод 1.21.4, `tests/mc_disasm.py`)

* `ClientPacketListener.handleSystemChat/handleDisguisedChat/handlePlayerChat/
  handleMovePlayer(ClientboundPlayerPositionPacket)/handleSetEntityMotion/handleLogin` и
  `ClientCommonPacketListenerImpl.handleCustomPayload/handleDisconnect/onDisconnect/
  onPacketError` — существующие методы с ровно теми дескрипторами, что стоят в `@Inject`
  (`check_mc_api`: 72/72 подписки колбэков, 0 пропущено; раньше «unresolved types» скрывал
  хендлер `onPacketError` — в `check_mc_api.py` добавлены типы `java.lang` в
  `JAVA_LANG_TYPES`, после чего подпись начала проверяться; отрицательный контроль:
  переставленные параметры дают ERROR и код 1).
* `onDisconnect` вызывают и `net.minecraft.network.Connection`, и
  `ClientCommonPacketListenerImpl` — значит он бывает в потоке netty; отсюда
  `AcdStore` со всеми мутациями под одним замком и `volatile`-политикой, а выключение
  сборки уходит в `client.execute`.
* `Window.setClipboardString` в 1.21.4 нет (0 совпадений по jar) — буфер обмена берётся
  через `Minecraft.keyboardHandler.setClipboard`; `RegistrationPayload` тоже нет, поэтому
  «сервер объявил канал античита» реализовано как id discarded-полезной нагрузки.
* `DisconnectionDetails` несёт только `reason/report/bugReportLink` — никакие
  «таймаут/пинг» не выводятся из пакета, и коллектор не делает вид, что различает их.

### Что сделано

* `swerve/acd`: `AcdCategory` (9 категорий, расширяется одной строкой), `AcdSeverity`,
  `AcdConfidence` (CONFIRMED/OBSERVED/HEURISTIC), `AcdEvent` (исходный текст отдельно от
  описания, лимиты 4096/512, пометка об обрезке), `AcdRule`+`AcdRules` (8 правил,
  исключающие маркеры, первое совпадение), `AcdClassifier` (`§`-коды, `Locale.ROOT`,
  окно поиска 2048), `AcdReport` (+`since` для окна выгрузки), `AcdStore` (кольцо
  50…20 000, склейка повторов, счётчики вытеснения/слияний, сессии), `AcdCollector`
  (десять источников, `emit` с фильтрами, `announce` в чат по настройке),
  `AcdFormatter` (текст + JSON + `paginate` с честной отметкой об обрезке), `AcdExporter`
  (буфер обмена, файл через `.tmp`+move, чат, очистка).
* `ActionSetting` (настройка-кнопка, в конфиг не пишется: `SettingCodec` отдаёт `null`),
  ветка `ActionSetting` и `ACT_ACTION = 31` в `MenuScreen`, регистрация в `ModuleManager`,
  `MixinClientCommonPacketListenerImpl` (4 хендлера) + 6 хендлеров в `MixinClientPacketListener`,
  `docs/AntiCheatDetector.md`.
* Обязательный сценарий выполнен архитектурно: `AcdStore` статический (история живёт вне
  модуля), все источники gated одним `volatile boolean`, а `openPopup`/`ACT_MODULE_OPEN`
  в `MenuScreen` не зависят от `isEnable()` — окно настроек выключенного модуля открывается,
  и `Copy All Logs` остаётся кликабельным. Проверено правил 13 `check_acd.py`.

### Дефекты, найденные и исправлённые в ходе работы (свои же)

* «Показывать важное в чате сразу» была декоративной: `AcdStore.announces()` не читался
  нигде — добавлен `announce` в `emit` (только новая запись, только WARNING/CRITICAL,
  только из игрового потока). Мутация «убить это чтение» теперь ловится (правило 12).
* `AcdFormatter` зависел бы от `AcdExporter` (формат-строки) — `render` переведён на
  булев признак, цикл пакетов убран.
* `AcdEvent.sameKey` не включал важность → эскалация `INFO → CRITICAL` проглатывалась
  слиянием; `merge` откатывал `lastTimeMs` назад при опоздавшем событии — оба исправлены.
* `AcdExporter.printToChat` молча терял хвост при переполнении (40 записей × ≤ 512
  символов > 60 кусков по 240) — разбивка вынесена в `AcdFormatter.paginate`, которая
  обязана поставить отметку «опущено строк: N из M, символов: K».
* `if flags.sessionContext() {` — собственная опечатка без скобок, найдена `check_syntax`
  (11 находок), а не глазами.
* `AcdCollector` импортировал `AntiCheatDetector` (наблюдающий пакет зависел от модуля) —
  заменено на `AcdStore.setStopHook`; правило 6 `check_acd.py` теперь ловит такую связь.

### Чем измерено

Первый прогон в игре (владелец, реальный сервер) — выгрузка JSON на 47 записей:
`merged: 155` (202 входящих события в 47 строк), `dropped: 0`, `heuristic: 0`, все

## 2026-10-25 — Speed: точка внедрения перенесена с подмены скорости на ускорение

### Зачем

`Speed` был единственным модулем движения без документа, без тестов и с подтверждёнными
дефектами (мёртвая настройка, двойное трение, условие коллизий с неправильным старшинством,
режим, который выбирает не всё). Задача ставилась как проверка корректности физики и
архитектуры; критерий «античит не заругался» из неё убран заказчиком, подбор значений или
порядка пакетов под пороги Grim не выполнялся (граница зафиксирована ниже и в `docs/Speed.md` §6).

### Что доказано (байткод 1.21.4, `tests/mc_disasm.py`)

1. `LivingEntity.travel(Vec3)` — только диспетчер: `travelInFluid` / `travelFallFlying` / `travelInAir`.
2. `travelInAir`: `friction = onGround ? Block.getFriction() : 1.0F`, `drag = friction * 0.91`,
   в конце `setDeltaMovement(motion.x * drag, y, motion.z * drag)`.
3. Ускорение приходит из `getFrictionInfluencedSpeed(f) = onGround ? getSpeed() * 0.216 / f³
   : getFlyingSpeed()` (0.02 для игрока), и у этого метода РОВНО ОДИН вызывающий —
   `handleRelativeFrictionAndCalculateMovement` (скан constant pool всего jar). Отсюда и точка внедрения.
4. `Player.getSpeed()` = атрибут `MOVEMENT_SPEED` (0.1); `LivingEntity.setSprinting` навешивает
   `SPEED_MODIFIER_SPRINTING` = +0.3 `ADD_MULTIPLIED_TOTAL` → 0.13. Спринт уже внутри
   масштабируемой величины, отдельного «спринт-члена» в `getFrictionInfluencedSpeed` нет.
5. Тот же `getSpeed()` читают `Player.attack` (отталкивание «длинного» удара через
   `getSpeed() * 2.5`), `LocalPlayer.updateAutoJump` и `travelInFluid`. Хук на `getSpeed()`
   затянул бы в изменения бой, авто-прыжок и плавание; хук на `getFrictionInfluencedSpeed` — нет.
6. `LocalPlayer.canStartSprinting` / `hasEnoughFoodToStartSprinting` /
   `hasEnoughImpulseToStartSprinting` / `shouldStopSprinting` — приватные. `KeyboardInput.tick()`
   читает `Options.keySprint`, а состояние спринта решается в `LocalPlayer.aiStep` ПОСЛЕ
   `input.tick()`; при этом `keyPresses.sprint()` в 1.21.4 не читает никто, так что «нажать
   клавишу спринта» через `MoveInputEvent` невозможно. Авто-спринт сделан через
   `@Invoker("canStartSprinting")`, а не репликой шлюза.
7. `BlockBehaviour$Properties`: трение по умолчанию 0.6, `speedFactor` 1.0; у льда 0.98
   (три блока в `Blocks.<clinit>`). `getBlockSpeedFactor()` читается в `Entity.move` — наш член не касается.

### Что решено и что изменено

- `modules/impl/movement/Speed.java` — переписан целиком. Ушли: пост-интеграционная подмена
  `deltaMovement`, «Трение», «Максимальная скорость», «Учитывать столкновения»,
  «Сохранять вертикаль», «Режим», «В воздухе», «Ускорение». Остались: «Множитель» (1.00…1.60),
  «Только на земле», «Только вперёд», «Авто-спринт». Модуль не хранит состояния между тиками,
  поэтому `onDisable` не нужен, а респавн/смена мира не оставляют «просроченного» решения.
- `mixins/client/MixinLivingEntity.java` — `@ModifyReturnValue` на `getFrictionInfluencedSpeed`
  (MixinExtras, без боксинга `float`), первым оператором — `(Object) this instanceof LocalPlayer`,
  потому что метод зовётся каждый тик для всех мобов.
- `mixins/accessor/LocalPlayerAccessor.java` — `@Invoker("canStartSprinting")`.
- Добавлены `docs/Speed.md`, `tests/check_speed.py`, `tests/check_speed_mutations.py`.
- `docs/NoWeb.md` §7: пункт про «`Speed` пишет `deltaMovement` в `onTick()` и перезатрёт наши
  значения» описывал старую реализацию — исправлен на соответствие текущей.
- `swerve.mixins.json` и `ModuleManager` НЕ менялись: новых миксин-классов нет, модуль уже
  был зарегистрирован.

### Попутно проверено (важно для `NoWeb` и для любых «скоростных» модулей)

`ServerGamePacketListenerImpl.handleMovePlayer` в 1.21.4: превышение бюджета
`100 * i` (квадрат накопленного смещения от `firstGoodX/Y/Z`, `i` — число необработанных
пакетов движения) приводит к `LOGGER.warn("... moved too quickly! ...")` и `teleport()` на
серверные координаты, то есть к **откату позиции**, а не к отключению; `disconnect`
с `multiplayer.disconnect.invalid_player_movement` — только за `NaN`/`Infinity`
(`containsInvalidValues`) и за «moved too quickly» у транспорта (`handleMoveVehicle`).
Комментарий `MAX_TICK_SPEED` в `NoWeb.java` («порог сервера d^2 > 100») по числу верен,
но формулировку последствий стоит уточнить владельцу — сам `NoWeb` в этой итерации не трогался.

### Решения и правки (все — по конкретному дефекту)

1. `utils/network/ServerTPS.java` — пороги вынесены в `PACKET_PERIOD_NS` /
   `RESYNC_NS = PACKET_PERIOD_NS * MAX_TPS`. Было `1e9` = ровно период пакета →
   любая лаг-выборка отбрасывалась, `tps()` возвращал 20 всегда, «Синхронизация по
   TPS» не работала. Формула не менялась (смена порога — и есть исправление).
2. `utils/player/MoveUtil.java` — `Mth.wrapDegrees` в двух сравнениях выбора
   направления. Измерение: сетка 720×720 (yaw × ввод), расхождение с корректным
   выбором в 3.15 % состояний, максимум ошибки курса 44.5°.
3. `utils/movement/ElytraFlightRotation.java` — guard `gcd <= 0 || NaN` в `fixRotate`
   (чувствительность 0 % → `round(x/0)*0 = 0` → залипание догонки). Формула GCD не
   тронута: она под паритетным тестом с AlphaDLC; отклонение задокументировано в
   `docs/ElytraFlight.md`.
4. `modules/impl/combat/KillAura.java` — `noHitThroughBlocks` учтён в ветке
   `smartHitbox` (раньше «Улучшить хитбоксы» молча отключало «Не бить через блоки»).

### Открытые вопросы
