# Speed

Модуль движения: множитель **ускорения** игрока. Не «ускорение через подмену скорости».

Файлы: `modules/impl/movement/Speed.java`, `mixins/client/MixinLivingEntity.java`
(обработчик `swerve$speedAcceleration`), `mixins/accessor/LocalPlayerAccessor.java`
(`@Invoker("canStartSprinting")` для авто-спринта).

## 1. Поведение

Пока модуль включён и условия ниже выполнены, ванильное приращение скорости за тик
умножается на «Множитель». Всё остальное — трение блока, гравитация, коллизии,
шаг через блоки, плавание, элитры, транспорт — считает vanilla без изменений.

Условия, при которых множитель **не** применяется:

| Условие | Почему |
| --- | --- |
| значение «Множитель» ≤ 1.00 | модуль не должен тормозить; при 1.00 поведение побитово ванильное |
| ускорение = 0 или не `Float.isFinite` | `NaN` из `travel` расходится по всей позиции и лечится только респавном |
| сущность — не местный игрок (`entity != minecraft.player`) | хук стоит в `LivingEntity`, его зовут все мобы и другие игроки; сравнение по идентичности отсекает и старого игрока после смерти/смены мира, и `ServerPlayer` в одиночной игре |
| `abilities.flying` | полёт в креативе/спектейторе — отдельный режим, там множитель дал бы скачок без причины |
| `isPassenger()` | верхом ускорение считает животное (`getRiddenSpeed`) |
| «Только на земле» и `!onGround()` | ограничение по настройке |
| «Только вперёд» и нет импульса вперёд | ограничение по настройке; читается `ClientInput.hasForwardImpulse()`, то есть уважает доворот камеры в SpatialGui |

Момент применения — не «тик», а непосредственно вычисление ускорения в `travel()`,
поэтому состояние между тиками не хранится: у модуля нет `onDisable`-уборки,
нет рассинхрона после респавна и нет «просроченного» решения, принятого на прошлом тике.

## 2. Физика 1.21.4

Всё ниже получено разбором байткода `minecraft-merged-a172fc6613-1.21.4`
(`Swerve/tests/mc_disasm.py`), а не из описаний в вики.

```java
// LivingEntity.travel(Vec3) — только диспетчер:
//   жидкость -> travelInFluid, элитры -> travelFallFlying, иначе -> travelInAir
// LivingEntity.travelInAir(Vec3 input)
BlockPos below = getBlockPosBelowThatAffectsMyMovement();
float friction = onGround() ? level.getBlockState(below).getBlock().getFriction() : 1.0F;
float drag = friction * 0.91F;
Vec3 motion = handleRelativeFrictionAndCalculateMovement(input, friction);
// ... гравитация getEffectiveGravity(), левитация, дно мира ...
setDeltaMovement(motion.x * drag, y, motion.z * drag);     // если !shouldDiscardFriction()

// LivingEntity.handleRelativeFrictionAndCalculateMovement(Vec3 input, float friction)
moveRelative(getFrictionInfluencedSpeed(friction), input); // <-- сюда попадает множитель
setDeltaMovement(handleOnClimbable(getDeltaMovement()));
move(MoverType.SELF, getDeltaMovement());
// ... далее ветка с horizontalCollision / jumping / onClimbable / powder snow —
//     она про подъём вдоль стены; в нашу модель не входит и нами не трогается.

// LivingEntity.getFrictionInfluencedSpeed(float friction)   [приватный, дескриптор (F)F]
return onGround() ? getSpeed() * (0.216F / (friction * friction * friction))
                  : getFlyingSpeed();                       // 0.02F для игрока вне полёта
```

`Player.getSpeed()` = значение атрибута `MOVEMENT_SPEED` (0.1; спринт —
`LivingEntity.SPEED_MODIFIER_SPRINTING` = +0.3 `ADD_MULTIPLIED_TOTAL`, то есть 0.13),
поэтому спринт уже внутри той величины, которую мы масштабируем.
Значение по умолчанию `Block.friction = 0.6`, `Block.speedFactor = 1.0`
(`BlockBehaviour$Properties.<init>`), у льда 0.98 (`Blocks.<clinit>`, три блока).

Отсюда смещение за тик `d_n = d_(n-1) * drag + a`, предельная скорость
`d* = a / (1 - drag)`. Она **линейна по `a`**, значит линейна и по нашему множителю —
это и есть содержательное свойство выбранной точки внедрения (проверяется числом, §8):

| сценарий | `d*`, блоков/тик | блоков/сек | при «Множитель» = 1.6 |
| --- | --- | --- | --- |
| земля (трение 0.6), ходьба | 0.2203 | 4.405 | 0.3524 |
| земля (трение 0.6), спринт | 0.2863 | 5.727 | 0.4581 |
| лёд (трение 0.98), спринт | 0.2757 | 5.515 | 0.4412 |
| воздух (член 0.02) | 0.2222 | 4.444 | 0.3556 |

Цифры 4.317 (шаг) и 5.612 (спринт) блока/сек — общедоступная оценка, здесь она не
проверялась; расхождение с моделью около 2 %, и важно его направление: модель скорость
слегка ЗАВЫШАЕТ, то есть границы, посчитанные по ней, получаются с запасом.

Время выхода на плато (тот же интегратор, 95 %): обычный блок — 5 тиков, лёд — 26,
воздух — 32. Столько же нужно на торможение: обратный ход симметричен, потому что
ускорение входит в одно и то же звено.

Верхняя граница множителя 1.6 — исходя из ванильного лимита перемещения, такого, каким
он оказался в 1.21.4 (разбор `ServerGamePacketListenerImpl.handleMovePlayer`):

- накопленный квадрат смещения от `firstGoodX/Y/Z` сравнивается с `100 * i`, где
  `i = receivedMovePacketCount - knownMovePacketCount` (в норме 1; при `i > 5` сервер пишет
  «sending move packets too frequently» и берёт `i = 1`); для летящего на элитрах
  (`isFallFlying()`) множитель порога — 300;
- при превышении — `LOGGER.warn("{} moved too quickly! {},{},{}")` и `teleport(...)` на
  серверные координаты, то есть **откат позиции**, а не отключение;
- `NaN`/`Infinity` в позиции или углах (`containsInvalidValues`) — вот это `disconnect`
  с `multiplayer.disconnect.invalid_player_movement`; отключение за «moved too quickly»
  в 1.21.4 есть только у транспорта (`handleMoveVehicle`);
- входящие координаты зажимаются `clampHorizontal` = ±3.0E7 и `clampVertical` = ±2.0E7.

При 0.4581 блока/тик (худший случай модели на множителе 1.6) квадрат смещения за тик
0.21, то есть бюджет в 100 единиц исчерпывается лишь на 476-м необработанном пакете.
Запас по этому критерию позволил бы поднять множитель и выше; 1.6 ограничивает не
риск отключения, а здравый смысл ползунка: дальше прирост скорости медленнее, чем
растёт цена ошибки. Никакого подбора под пороги античита в модуле нет и быть не может — см. §6.

Почему нет «плавного разгона» (RATE-LIMIT на сам множитель): он не нужен. Значение
входит в апериодическое звено, поэтому скачок множителя меняет только приращение, а
скорость догоняет новое значение монотонно и без перелёта (проверяется числом, §8).
Старая реализация (см. §4) этого свойства была лишена в принципе.

## 3. Точка внедрения и альтернативы

Выбрана `LivingEntity.getFrictionInfluencedSpeed` — единственный член, который читает
ускорение игрока: у него ровно один вызывающий (`handleRelativeFrictionAndCalculateMovement`),
проверено сканом константных пулов всего jar.

| Вариант | Что пробовали | Почему отвергнут |
| --- | --- | --- |
| `@Inject` в `Module.onTick()` + `setDeltaMovement` | прежняя схема модуля | `onTick` выполняется на END_CLIENT_TICK, то есть **после** `travel()` и после `sendPosition()`: изменение дельта-вектора уходит в пакет следующего тика, а ваническое трение накладывается поверх ручной коррекции. Плюс пост-интеграционное домножение расходится на блоках с высоким трением (§4, пункт 3) |
| `Player.getSpeed()` | самый простой хук | масштаб затронул бы и `Player.attack` (отталкивание/«длинный» удар при спринте читает `getSpeed() * 2.5`), и `LocalPlayer.updateAutoJump`, и `travelInFluid` (плавание). То есть боевые и вспомогательные механики поехали бы вместе со скоростью |
| масштабирование `forwardImpulse`/`leftImpulse` через `MoveInputEvent` | уже есть в клиенте | невозможно: `Entity.moveRelative` нормирует ввод при длине > 1, поэтому импульс выше 1 дать нельзя, а ниже — значит тормозить |
| `@ModifyVariable` на аргумент `friction` в `travelInAir` | одно число, «красиво» | меняет трение, а не ускорение: вместе с разгоном поехала бы и тормозная характеристика, и прыжковая помощь в `handleRelativeFrictionAndCalculateMovement` |

Формулировка, которую можно проверить глазами: мы меняем **`a`**, а не **`v`**.

Миксин — `@ModifyReturnValue` (MixinExtras 0.5.4, уже используется в `MixinLocalPlayer`),
поэтому обработчик не боксит `float` и не тащит `CallbackInfoReturnable`, как это сделал бы
обычный `@Inject` в методе с примитивным возвратом. Проверка типа
`(Object) this instanceof LocalPlayer` стоит первой строкой: метод вызывается каждый тик для
каждой живой сущности в чанках, и для мобов всё остальное в обработчике — пустая работа.

## 4. Исправленные дефекты прежней реализации

1. **«Сохранять вертикаль» не делал ничего**: в обеих ветках `if`/`else` вызывался
   один и тот же `setDeltaMovement(x, movement.y, z)`. Настройка удалена; вертикаль
   в новой схеме не касается модуля по построению.
2. **Двойное трение**: `applyFriction()` домножал `deltaMovement` на «Трение», тогда как
   `travelInAir` уже применил `friction * 0.91`. Теперь модуль трение не трогает.
3. **Расходящийся ряд**: при домножении уже проинтегрированной скорости знаменатель
   прогрессии становится `k * drag`, а не `drag`. На льде (`drag = 0.98 * 0.91 = 0.8918`)
   при `k = 1.15` он равен 1.0256 > 1 — скорость росла бы до бесконечности, если бы её
   каждый тик не прибивал вверх-вниз clamp «Максимальная скорость» (в модели: 0.326 →
   0.776 → 2.934 → 47.68 блоков/тик за 100 тиков). Отсюда же брались рывки у стены.
4. **Приоритет в условии столкновений**: `horizontalCollision || verticalCollision && !onGround()`
   из-за старшинства `&&` означало «игнорировать любую горизонтальную коллизию, но
   вертикальную — только в воздухе». Флаг «Учитывать столкновения» удалён: коллизии
   решает `Entity.move`, а не модуль.
5. **Режим выбирал не всё**: `groundMultiplier`/`multiplier` читались до проверок режима,
   поэтому «Ваниль» и «Земля» влияли только на часть поведения, а «Страф»/«Земля»
   отличались одной строчкой раннего возврата.
6. **`setSprinting(true)` вне ванильного шлюза** и `setSprinting(sprint.get())` в режиме
   «Ваниль» — модуль переписывал состояние игрока, в том числе выключал спринт, который
   включил сам игрок или другой модуль. Теперь спринт поднимается только если на это
   согласна сама игра: `LocalPlayer.canStartSprinting()` (через `@Invoker`) плюс ванильное
   требование «земля или из-под воды». Гасить спринт модуль не имеет права.
7. **Не было `onDisable`**: состояние (множитель, спринт) жило только в `deltaMovement`.
   Теперь состояния нет — вопрос снят, а не закрыт костылём.
8. **Не было ни `visible(...)`-связок, ни документа, ни тестов.** Настроечные обещания
   вида «Ускорение» (0.001…0.15) и «Трение» существовали только как ползунки.

## 5. Настройки и миграция конфига

| Настройка | Тип | По умолчанию | Диапазон | Смысл |
| --- | --- | --- | --- | --- |
| «Множитель» | `FloatSetting` | 1.15 | 1.00 … 1.60, шаг 0.01 | во сколько раз больше ванильное приращение скорости за тик |
| «Только на земле» | `BooleanSetting` | false | — | в воздухе не ускорять (прыжок всё равно сохраняет набранное: `travelInAir` в воздухе гасит `drag = 0.91`) |
| «Только вперёд» | `BooleanSetting` | false | — | только при импульсе вперёд |
| «Авто-спринт» | `BooleanSetting` | true | — | поднимать спринт, когда это разрешено ванильным `canStartSprinting()` |

Удалены: «Режим», «Множитель на земле», «Ускорение», «Максимальная скорость», «Трение»,
«Сохранять вертикаль», «В воздухе», «Учитывать столкновения». Из них осмысленное
наследие осталось у двух: «Только на земле» = прежний «Земля», «Множитель» = прежние
«Множитель»/«Множитель на земле» одним ползунком, потому что разделение «земля/воздух»
было артефактом пост-интеграционной подмены (в воздухе нужно было «добрать» скорость
руками; теперь тот же член работает в обеих фазах).

Миграция конфига: `ConfigManager` сопоставляет значения по именам настроек, неизвестные
ключи игнорируются, отсутствующие получают значения по умолчанию. Формат не менялся
(`FORMAT = 1`), поэтому старый `config.json` читается: лишний ключ просто никогда не
читается — `applySettings` идёт по списку настроек модуля и ищет их в JSON, а не наоборот.
Значение «Множитель» из старого файла подхватится (и будет зажато в 1.00…1.60), остальные
останутся по умолчанию. «В воздухе» → инверсия «Только на земле» вручную не переносится —
это надо знать тем, у кого стоял режим «Земля». В `run/config/swerve/config.json`
(артефакт локального запуска, лежит в репозитории) до первой же записи конфига останутся
старые ключи `Speed` — это безвредно, и трогать его в этой правке не стали: там пользовательские
значения запуска.

## 6. Сервер и античиты

Что сервер видит физически: клиент сам считает своё положение (кроме транспорта и
нескольких частных случаев), а Speed меняет только **скорость нарастания** смещения.
Ванильный сервер проверяет это смещение по трём критериям, перечисленным в §2:
корректность значений (отключение), границы мира (зажимание) и бюджет `100 * i` на
накопленное расстояние (откат телепортом). Наихудший случай модели — 0.4581 блока/тик,
то есть до отката запас примерно в 470 необработанных пакетов (§2). Атрибут
`MOVEMENT_SPEED` клиента серверу неизвестен: локальное масштабирование ускорения не меняет
состояние на сервере, откатывать ему нечего, пока бюджет не исчерпан.

Именно поэтому здесь **нет** раздела «как это проходит проверку». Любое ускорение сверх
того, что сервер может объяснить разрешёнными ему средствами, — расхождение с моделью,
и любой предиктивный античит (GrimAC в том числе, разбор — `docs/GrimAC.md`) эту разницу
видит: он пересчитывает тик по своей копии физики и сравнивает. Никакой подбор
«Множитель» под пороги, порядок пакетов или переиспользование скорости откатов в этом
модуле не реализованы и реализованы не будут; это не свойство кода, а граница задачи.

Что модуль делает честно и осознанно: не трогает пакеты (ни порядков, ни содержимого,
кроме штатного `sendPosition`, который делает игра), не шлёт лишних пакетов, не меняет
состояния, кроме одного флага спринта (он и в ванилле отправляется как
`ServerboundPlayerCommandPacket`, а не как «ещё один канал»), и не оставляет следа
после выключения.

## 7. Взаимодействие с другими модулями

- **KillAura** — «Сбрасывать спринт» (`setSprinting(false)` после удара) и наш
  «Авто-спринт» работают в разных фазах: аура гасит в момент удара, Speed поднимает на
  следующем тике, если на это согласен `canStartSprinting()`. Ровно так же ведёт себя
  игрок с зажатой клавишей, конфликта «кто кого перебил за один тик» нет.
- **ElytraFlight / ElytraFlightRotation** — полёт на элитрах идёт через `travelFallFlying`,
  наш член в этой ветке не участвует. До- и пост-полёт (земля) ускоряются на общих основаниях.
- **NoWeb** — компенсация паутины трогает `deltaMovement`, мы — ускорение; одновременная
  работа даёт сумму эффектов, взаимной отмены нет.
- **`MixinKeyboardInput` (SpatialGui, `MoveInputEvent`)** — наш шлюз «Только вперёд»
  читает `ClientInput.hasForwardImpulse()`, который в этом миксине переопределён под
  доворот камеры; то есть признак «иду вперёд» совпадает с тем, что использует аура.
  Обработчик Speed в `KeyboardInput.tick` не вмешивается: у него там нет дела.
- **ConsumableUseController** — при использовании предметов `canStartSprinting()`
  возвращает false (`isUsingItem()`), так что авто-спринт во время еды/зелья не включается.
- **Креатив/спектейтор** — исключены явно (§1), чтобы не ломать привычную скорость полёта.

который обязан падать на старой схеме (знаменатель `k * drag > 1` на льду);
(3) структуру кода: запрет `setDeltaMovement`/`getDeltaMovement`/`Vec3` в модуле,
полный набор guard'ов, порядок проверок, одновладение целью миксина, `try/catch`
с логом и `setEnabled(false)`, `@Invoker("canStartSprinting")`, уникальность и
«русскость» имён настроек, совпадение границ ползунка с константой `MAX_MULTIPLIER`,
целостность документа (разделы, заголовок «НЕ ПРОВЕРЕНО», отсутствие формулировок про
обход античита), а также отсутствие в комментариях и тексте смешения кириллицы с латиницей
и символов посторонних письменностей.

`check_speed_mutations.py` вносит по одной поломке во временную копию файлов (репозиторий
не трогается) и требует, чтобы `check_speed.py` её нашёл: 18 мутаций — вернули
`setDeltaMovement`, убрали `isEnable`, сняли защиту от `NaN`, убрали сравнение с
локальным игроком, расширили ползунок за `MAX_MULTIPLIER`, убрали шлюз «Только вперёд»,
поставили спринт мимо `canStartSprinting`, включили `setSprinting(false)`... — все 17
пойманы, контрольный прогон чист. Две последних мутации (латинское слово и иероглиф в
русском тексте) вносятся не по якорю-фразе, а в первое найденное кириллическое слово: иначе
любая правка формулировки превратила бы проверку в «сломанный прогон».
Первый прогон этого механизма дал 16 из 17: проверка
«в документе есть НЕ ПРОВЕРЕНО» находилась подменой заголовка, потому что искала фразу
в любом месте текста (само описание в §8 содержало её) — требование ужесточено до
заголовка, и этот случай теперь тоже в списке мутаций.

## 9. Чек-лист ручной проверки перед выпуском

Требует JDK 21 и запуска клиента: `./gradlew build` и `./gradlew runClient`.

1. Сборка проходит, в логе загрузки нет ошибок применения миксинов (`Mixin apply failed`,
   `InvalidInjectionException`) на целях `getFrictionInfluencedSpeed` и `canStartSprinting`;
   при `defaultRequire: 1` незакрытая цель видна сразу.
2. «Множитель» = 1.00: движение неотличимо от ванильного (сравнить с выключенным модулем
   на прямом пути и при приземлении).
3. «Множитель» = 1.60, прямой разбег: разгон плавный, плато на обычном блоке за ~5 тиков,
   на льду и в воздухе ~26–32 (модель §2), рывков и «протяжки» назад нет; `F3` → `pos`
   меняется без скачков.
4. Стена: при упоре в блок нет дрожания и самопроизвольного отскока (проверка на то, что
   модуль больше не дерётся с коллизиями).
5. Лёд/синий лёд: скорость не растёт от тика к тику (контроль расходящегося ряда из §4.3).
6. Прыжок через блок: после отрыва скорость не падает в ноль и не растёт скачком.
7. Вода: вход в воду не даёт ускорения (плавание не масштабируется), выход — восстанавливает.
8. Элитры, транспорт, креатив-полёт, спектейтор: поведение не изменилось.
9. «Только на земле» + прыжок; «Только вперёд» + стрейф; «Авто-спринт» на голоде ≤ 6
   (спринт не включается) и с едой (включается один раз, без мигания).
10. Выключение на ходу: через 1…2 тика скорость ванильная, зажим клавиши спринта не «залипает».
11. `config.json` со старыми ключами модуля читается без предупреждений, новые значения
    сохраняются и переживают перезапуск.

## НЕ ПРОВЕРЕНО

- **Не скомпилировано.** В песочнице нет JDK 21 и нет доступа к Maven Central
  (`repo1.maven.org` недоступен), поэтому `./gradlew build` не запускался. Проверены
  только структура и API: `check_mc_api.py` сверяет имена/дескрипторы микшируемых целей
  и сигнатуры обработчиков с настоящим jar'ом 1.21.4, `check_syntax.py`/`check_types.py`
  — разбор и разрешение имён. Это **не** доказательство ни компиляции, ни рантайма.
- Не проверено применение миксинов в рантайме (MixinExtras `@ModifyReturnValue` к
  **приватному** методу `getFrictionInfluencedSpeed` — по документации Mixin приватные цели
  поддерживаются, но факт применения здесь не наблюдался).
- Числовая модель — упрощение: в ней нет нормировки ввода, `handleOnClimbable`,
  прыжковой помощи у стены, `getBlockSpeedFactor()` внутри `Entity.move` и округлений
  `float`. Оценки §2 годятся для границ и сравнения вариантов, но не как эталон для
  подгонки значений.
- Реакция серверов и античитов на ускоренное движение не измерялась: нет ни сервера,
  ни клиента. В §6 описано только то, что следует из кода ваниллы 1.21.4.
- Не проверялись: поведение при `horizontalCollision` на лестницах/около краёв,
  взаимодействие с плагинами на `ServerboundPlayerCommandPacket`, и то, как модуль
  ведёт себя при TPS < 20 (там ускорение считается по тикам, а не по времени).
- Не проверялось, что удалённые имена настроек больше нигде не упоминаются в GUI-тултипах
  и описаниях: `check_config.py` даёт 0 находок, но он проверяет имена внутри модулей,
  а не перекрёстные ссылки текста описаний.
