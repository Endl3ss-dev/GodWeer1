# Scaffold / Telly Mode (experimental)

Это игровой контроллер внутри существующего **Scaffold**, а не Coach и не обученная
нейросеть. Default `Telly Mode = false`: старый edge Scaffold / Jump Assist сохранён.

## Использование

1. Одиночный тестовый мир, безопасная площадка над землёй; сервер 20 TPS,
   клиентский timer 1x. Выключить Coach и остальные gameplay-модули.
2. Положить в основную руку полный строительный BlockItem (например, шерсть/камень).
   Автовыбор hotbar в Telly Mode намеренно не выполняется.
3. На платформе повернуться вдоль X/Z будущего моста. В Scaffold включить
   `Telly Mode`, затем сам Scaffold. Удерживать только W, без RMB/Alt/Space:
   режим сам запрашивает sprint/прыжок перед краем, поворачивает видимую камеру,
   пытается поставить до трёх блоков на фиксированной высоте в одном ряду и
   возвращает камеру вперёд. W остаётся разрешением продолжать движение.
4. Отпускание W, боковой/обратный ввод, sneak, потеря фокуса, GUI, смена мира,
   конфликт модулей/таймера прерывают цикл. Для нового старта выключить/включить
   Scaffold на платформе. После падения тоже перезапустить на платформе.

## Связь с записями

`tools/analyze_telly_episodes.py` выделяет завершённые ground→air→ground эпизоды,
не пересекает segment, дедуплицирует клетки и проверяет одну высоту, прямую и
непрерывность. Среди четырёх загруженных записей найдено **27 кандидатов** с 3+
блоками. Это локальные наблюдения, не доказательство серверного успеха и не
автоматическая разметка «идеального Telly». Результат:
`docs/telly-episode-analysis.json`.

У кандидатов медианная длительность 12 клиентских тиков; медианные смещения первых
трёх установок 4/7/10 тиков. Они использованы как нижние границы попыток, а не как
воспроизведение задержек реального времени. Видимая доводка ограничена 90°/тик,
возврат — 60°/тик: это инженерные настройки прототипа, не обученные параметры.
Расстояние запуска прыжка 0.85 блока — также эвристика, а не измеренная модель.

Состояния: RUN → TAKEOFF → BUILD → WAIT → BUILD/RETURN → RUN; HALT при прерывании.
Каждый клик требует актуального raycast на выбранную грань в пределах reach,
допустимой цели, полного опорного блока и предмета. После поворота клик отложен до
следующего тика для обычной передачи видимого направления. WAIT проверяет локальное
появление полного блока; никаких обещаний server acknowledgement нет.

## Ограничения и проверки

Это **пробная реализация**, а не проверенный Speed Telly. Не гарантирует три блока
в каждом прыжке: геометрия и длительность прыжка могут не дать поставить все три.
Движение корректируется относительно направления моста, скорость/позиция напрямую
не меняются. На приземлении возврат камеры задерживает новый разгон. Остановка ввода
не обнуляет инерцию: использовать только над безопасной площадкой. Режим не предназначен
для multiplayer, диагоналей, лестниц, tower или автоматического восстановления падения.

Добавлены Java-проверки расписания и cardinal heading в `testScaffold`, а также
Python-регрессии извлечения эпизодов. В среде агента нет Java/Javac: компиляция и
игровая проверка не выполнены. Синтаксический parser не проверяет Minecraft API.

Ручная проверка: четыре cardinal направления; обычный Scaffold при Telly OFF;
пустой слот/неполный блок; отпускание W; GUI/focus; Coach/Timer/TPS 3; respawn/world;
проверить отсутствие двойных кликов и изменения высоты ряда, затем короткий мост
на 1x. Не использовать длинный мост до этой проверки.

## Источники

Основной источник — собственные загруженные JSONL; API взят из текущего
ScaffoldModule (Input, useItemOn, raycast). Для прежней реализации проверялись
https://docs.fabricmc.net/26.2/develop/key-mappings и YouGame-материалы
https://yougame.biz/threads/117562/ — подходящего современного лицензированного
Telly-кода не найдено, чужой код не переносился. Новых зависимостей клиента нет.
